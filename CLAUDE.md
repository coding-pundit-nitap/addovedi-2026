# CLAUDE.md

Project-specific context for Claude Code sessions in this repo. See [README.md](README.md) for frontend onboarding/setup and [REGISTRATION.md](REGISTRATION.md) for the registration system's design.

## Stack & structure

- `client/`: React + Vite, Three.js (react-three-fiber + drei) for the 3D hero scene, Zustand for state, Tailwind for styling, Framer Motion for 2D animation.
- `server/`: Node.js + Express + MongoDB (Mongoose). `server/controllers`, `server/models`, `server/routes`, `server/middleware`, `server/services`, `server/utils`.
- Client install requires `npm install --legacy-peer-deps` inside `client/` (strict 3D-library peer deps — see README).

## Deploy flow

- **Frontend**: Vercel, auto-deploys on push to `main`.
- **Backend**: Render, **manual trigger only** — pushing to `main` does NOT redeploy it. Any change under `server/` needs an explicit Render redeploy to go live.
- `TURNSTILE_SECRET_KEY` (server) / `VITE_TURNSTILE_SITE_KEY` (client) are set on Render/Vercel for the Cloudflare Turnstile CAPTCHA on signup.
- **Self-hosted college-server path (added 2026-10-09, alternative to the above, not yet used)**: `docker-compose.yml` at repo root builds three app containers (`mongo`, `server`, `client`) behind a fourth, `nginx/`, which is the only one published to the host and reverse-proxies `/api/*` to `server` and everything else to `client`'s own internal nginx. `mongo` has no auth and is internal-network-only — fine behind the single `nginx` port, but add Mongo auth first if the college server is multi-tenant/shared. Copy `.env.production.example` to `.env` in the repo root, fill in real secrets, then `docker compose up -d --build`; only `NGINX_PORT` (default 8080) needs to be reachable. Vite's `VITE_*` vars are baked in at the client's build time via Docker build args, not container env vars. This setup was written and manually traced against the real source (ports/env var names) but never build-tested — Docker isn't installed in the sandbox this was built in.

- **Database for Docker**: `MONGODB_URI` in the root `.env` is passed through by `docker-compose.yml` (default: bundled `mongo` container). Set it to the Atlas string to serve the same data as Render; allow the server IP in Atlas Network Access.
- **Backups** (2026-10-09): `node scripts/backup.js` (from `server/`) writes every collection to `backups/<UTC timestamp>/*.json.gz` (gitignored, contains personal data + password hashes; keeps newest 14). `node scripts/restoreBackup.js <folder> [--confirm]` restores (dry run without `--confirm`), also the way to move Atlas data into the college server's Mongo. In Docker: `docker compose exec server node scripts/backup.js` lands in `./backups` on the host (volume-mounted). The college-server Mongo is a separate empty DB from Atlas: restore a backup into it before going live, and cron the backup nightly.

## Key systems

- **Participant accounts**: real server-backed accounts (`GlobalUser` model) with guaranteed-unique Addovedi IDs — not localStorage. Registration status (`PENDING_UNSTOP_VERIFICATION` / `VERIFIED` / `CANCELLED`) is fetched live from `GET /registrations/my/:addovediId` (`server/controllers/registrationController.js` → `getMyRegistrations`), which returns every registration an Addovedi ID is part of as leader OR team member. `client/src/utils/registrations.js` wraps this fetch. Only the team leader can cancel a registration (enforced both client- and server-side via leaderUID+leaderPhone match).
- **Team invites** (added 2026-10-09): `Registration.members[].status` = PENDING/ACCEPTED/REJECTED (legacy members default ACCEPTED). Leader registers teammates as PENDING; each teammate accepts/declines via `POST /registrations/respond` (frozen once admin marks VERIFIED). A declined member frees their slot (dup checks use `$elemMatch` status != REJECTED). `GET /registrations/my/:id` and register/cancel/respond all require the participant JWT; only the leader sees teammate statuses; admin lists show them. Site-wide `InviteBar.jsx` (mounted in App.jsx) polls every 20s and shows pending invites with Accept/Decline; Player HQ shows a banner too. **Render redeploy needed.**
- **Passwords** (2026-10-09): no email service exists, so recovery is admin-assisted. Players tab → profile → RESET PASSWORD (`POST /participants/:id/reset-password`, admin only) returns a one-time temp password and sets `mustChangePassword`; the player must set their own via `ChangePasswordPanel.jsx` (`POST /participants/change-password`); until then every other participant route returns 403 MUST_CHANGE_PASSWORD (`requireParticipant`). Any change/reset stamps `passwordChangedAt`, which `requireParticipant` uses to reject older tokens. Forgotten Addovedi ID: log in (shown on profile) or admin searches Players by name/email/phone. **Render redeploy needed.**
- **Admin dashboard** (`client/src/components/admin/AdminPage.jsx`): sessions expire after 12h; fetch functions must handle non-OK responses explicitly (force logout + "SESSION EXPIRED") rather than silently showing empty lists — this was a real bug (fixed in commit 5c9ac0a).
- Duplicate-registration checks and "all registrations for an Addovedi ID" queries rely on indexes with a case-insensitive collation (`{ locale: 'en', strength: 2 }`) on `Registration` — see `server/models/Registration.js`. Don't add a new cross-event or cross-user lookup without an index to match, it'll silently become an O(n) scan at scale.
- **Timeline scheduling**: the public Timeline page (`client/src/components/timeline/TimelinePage.jsx`) is admin-controlled, not hardcoded. `SubEvent.timeline` (`server/models/SubEvent.js`) holds `{ day: 1|2|3|null, time, end, venue, mode, prize }` per sub-event, edited from Admin's "Timeline Scheduling" section on the sub-event form. `day` is a bucket index (1/2/3), not a literal calendar day-of-month — the calendar dates/labels for those buckets live in one place, `DAY_META` in `client/src/data/events.jsx`, and `buildTimelineDays()` rebuilds the three-day schedule from live DB data (falls back to the static hardcoded schedule only when the DB has zero sub-events). An event with `timeline.day` unset is simply left off the Timeline page — that's the correct "not scheduled yet" state, not a bug. Event LIVE/UPCOMING/COMPLETED status is computed automatically from real time vs. the scheduled time, not admin-set.
- **Event dates**: Day Zero = Oct 28 2026 (starts 5PM) / Day 1 = Oct 29 / Day 2 = Oct 30. These map to `timeline.day` values 1/2/3 respectively via `DAY_META` (see above) — if dates change again, only `DAY_META` needs editing, nothing else.
- **Participant JWT auth** (added 2026-10-09): `GlobalUser` signup/login (`server/services/globalUserService.js`) return a 30-day participant JWT alongside the user object. `PUT /participants/profile/:id` requires it via `requireParticipant` (`server/middleware/auth.js`), which decodes the token and rejects it if `role !== 'participant'` or the decoded id doesn't match `:id` — the client no longer proves identity with a spoofable `email` body field. Admin tokens (`protect` middleware, same file) share one `JWT_SECRET` with participant tokens but carry `role: 'admin'`, and each middleware rejects the other role's token, so one secret can't be used to cross admin/participant privilege. `PortalPage.jsx` stores the token inside the `addovedi_user` localStorage blob and sends it as `Authorization: Bearer <token>`; since the profile-update response is a fresh DB read with no token field, the client re-attaches the existing token after that call instead of letting it get wiped from storage.

## Conventions learned

- **Mobile breakpoints**: this codebase tends to default to Tailwind's `lg:` (1024px) for switching from stacked to multi-column/desktop layouts, which leaves a dead zone around 768–1023px (tablet/small-laptop) where content stacks into a narrow column on an otherwise-wide screen. Prefer `md:` (768px) unless there's a specific reason for `lg:`. Also watch for hardcoded pixel `minHeight`/fixed avatar sizes that don't get reduced/removed on mobile, and headings that wrap awkwardly against an adjacent badge instead of stacking.
- The Hero page (`client/src/components/hero/HeroOverlay.jsx` + `client/src/three/Scene/IntroSequence.jsx`) is a timed cinematic intro: navbar/logo/button are hidden (`showNavbar`/`showLogo`/`showButton` in Zustand, all default `false`) until a GSAP timeline reveals them at ~4–6s. A near-blank screen in the first few seconds on `/home` is expected, not a bug.
- **First-visit loading screen** (`client/src/components/common/FirstLoadScreen.jsx`, mounted in `App.jsx`): shown once per browser session (`sessionStorage.addovedi_loaded`), DOM/CSS-only so it doesn't lag while models parse; progress is the real drei `useProgress` value with a 2.4s minimum / 15s cap. The Hero intro timeline in `IntroSequence.jsx` waits on the Zustand `appReady` flag, so the cinematic starts after the loader fades, not behind it. Heavy category models are preloaded in the background after it dismisses.
- **Per-event team size** (added 2026-10): `SubEvent.minTeam`/`maxTeam` (leader included; equal = fixed, e.g. BGMI 4/4), editable in Admin's sub-event form. Enforced server-side in `createRegistration` (`registrationController.js`) and used by `RegistrationForm.jsx` to limit the Team Size picker. Events with no DB record (static fallback only) have no limit. **Render redeploy needed.**
- **3D models are optimized** (`client/public/models/*/scene.glb`, ~7MB total, meshopt-compressed; most had textures stripped because their showcases replace materials with wireframes; portal and clock keep textures). Never feed the raw cached `useGLTF` scene to a component that mutates it: use `useClonedScene` (`HologramCards.jsx`) / `cloneScene`, otherwise models mutate each other and misalign until a hard refresh. Original GLBs live in git history before commit `3af5a95`.
- **Launch switches** (`SiteSettings` model, `/api/settings/registration` and `/api/settings/crew`, public GET / admin PUT): `registrationOpen` and `crewVisible` both default to **false**, so a fresh site shows "Registration starting soon" in the event modal and "Crew launching soon" on `/crew`. Admin flips them with the toggles at the top of the Event Registrations and Crew Personnel tabs; the server also refuses new registrations while closed (403 `REGISTRATION_CLOSED`). Clients fail closed if the endpoint is unreachable (e.g. backend not redeployed). Hooks: `client/src/utils/useRegistrationOpen.js`. **Render redeploy needed.**
- **Admin Players tab** (`admin/PlayersPanel.jsx`, `GET /api/participants`, `DELETE /api/participants/:id`, both admin-only): lists every `GlobalUser` (never `passwordHash`) with event counts, search, and a profile modal listing the registrations they're part of as leader or member (computed client-side from the already-loaded registrations). Roster names/IDs in Event Registrations open the same modal. A player on any registration can't be deleted (409): delete those registrations first. **Render redeploy needed.**
- `git commit`/push to `main` is done directly (no PR requirement enforced, though GitHub shows a bypassable branch-protection rule); verify uncommitted work actually got pushed rather than trusting a prior session's own summary of what it did — check `git status`/`git log` directly.
- Dev server: `client` uses port 5173; a server may already be running from a terminal the user has open — check with `lsof`/the preview tool's own "port in use" message before starting a duplicate one.
- **Shared CSS across components is fragile here**: several components (`HeroOverlay.jsx`, `CommonSidebar.jsx`, `CommonNav.jsx`) each embed their own `<style>` block with raw CSS classes (`.reg-btn`, `.reg-fill`, etc.) that other components' JSX reuses by class name without defining the rule themselves, assuming whichever component happens to be mounted alongside provides it globally. This breaks silently (missing `position:relative`/`overflow:hidden` etc.) on any page/route where that other component isn't mounted. When adding a styled element, give the component its own copy of the CSS it needs rather than assuming another mounted component provides it.
- **Native `<input type="time">` is unreliable here**: Safari can flag it "invalid" on form submit if the field is still mid-focus when Save is clicked, even with a valid value typed. Prefer plain `<input type="text">` with a placeholder hint (e.g. "24h, e.g. 13:00") for time fields — matches how times are stored everywhere in this codebase anyway (plain "HH:MM" strings).
- **EventsPage/TimelinePage poll the DB** (`fetchEvents` every 4s, registrations every 8s) and rebuild derived objects (`activeEvent`, category lists) as brand-new references each cycle even when content is unchanged. Any `useEffect` elsewhere that depends on one of these objects wholesale (instead of a stable primitive like `.title`) will re-fire on every poll tick — this caused a real bug where the event modal's tab selection snapped back to "Register" a few seconds after the user clicked Overview/Rules (fixed in commit 1d5eae0). Depend on stable primitives, not the whole object, when reacting to "did the selected event change."
- When a browser-pane repro looks broken in a way that contradicts the code, check for a stale Vite HMR bundle before concluding it's a real bug — this session hit a case where `[hmr] Failed to reload ...` had left genuinely stale JS running; a hard reload (`location.reload(true)`) resolved it and the "bug" wasn't real.
- **Keep context usage light in this repo**: this is a small, low-traffic college techfest site, not a large/high-scale codebase — avoid re-reading large files or whole directories speculatively, prefer targeted `grep`/`Read` with offsets, and don't reach for subagents/broad exploration for things a direct lookup answers. The user explicitly asked for less token/cache-heavy sessions here.
